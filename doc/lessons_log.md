## L1. 评测与协议

- **L1.1 dev/test 配套错误是静默的**（2026-09-04）：`-e exact_match` 配 hellaswag 会跑通但分数全噪声（检查字母是否出现在续写里）。对策：所有启动脚本加 `-d`/`-e` 配套校验（sweep/run_lp/run_sgms 已内置）。
- **L1.2 赢者诅咒是真实的**（2026-09-04 hellaswag 旧 run）：200 条 dev 的 σ≈0.034，dev 上挑最大值天然 +1σ；dev 0.65 → test 0.562。对策：冠军复评（top-2 均值）+ 报告 test 终值 + 多种子。
- **L1.3 提升量低于噪声的结论不可信**（2026-09-05）：论文 hellaswag test 上涨（.601→.652，+5σ）而我们的 +0.025<σ 下跌——漂移是否发生取决于信噪比，不是必然。表述要条件化。
- **L1.4 等预算对比看"等效全量评测数"**：full + coarse×(coarse_size/200)。按迭代数叠图对多保真方法不公平。

## L2. 工程纪律

- **L2.1 multiprocessing 必须 spawn 不能 fork**（09-05 v1 崩）：父进程持 torch 张量状态时 fork，子进程死锁（全睡 futex、不读权重）。spawn 后一切正常。
- **L2.2 改代码必先 `--fake_eval` 干跑**（09-05 v1/v2 两连崩教训）：低概率分支（10% 的生成器④）和晚激活分支（≥30 观测的协同）在短冒烟里测不到；`rng.dirichlet`/`syn.rotate` 两颗雷都是路径覆盖问题。干跑要含重启、终选、test 全路径。
- **L2.3 日志 append 模式的坑**：重跑同目录 log.txt 会残留旧 FATAL，验证要用全新目录名。
- **L2.4 FATAL 守卫必装**：stderr 常被 /dev/null，崩溃现场必须写进 log.txt（v2 的 traceback 因此才拿到）。
- **L2.5 运行中脚本勿编辑**：bash 边读边执行；等行数替换 + 文件 <8KB 预读缓冲才安全。链式脚本间用 PID 等待解耦。

## L3. 搜索算法（核心经验）

- **L3.1 初始覆盖决定上限**（09-05 v3→v4）：10 专家+2 混合 → 10+10 后起始最优 0.625→0.640。起点多样性是"未控制的混杂变量"——对比实验必须对齐初始数量与预算。
- **L3.2 LP 输 hellaswag 的死因=覆盖失败**（09-05 离线分析铁证）：PSO 冠军距 LP 全部 176 观测最近 0.327；两冠军同在 flan+oasst 脊上但配比相反（距离 0.52）。不是空间自由度不够（box⊃仿射包），是**探索带宽不够**：局部生成器占 70-80%，远跳配额低且被粗筛过滤。
- **L3.3 二次代理只在数据附近有效**：R²=0.919 但 argmax 外推到 4.4 的荒谬值。代理只能提名、不能开放式优化；GP（RBF 回落先验）+ κσ 采集是正确替代。
- **L3.4 未探索区域被系统性低估**（09-05）：代理预测两个冠军 0.664/0.655 vs 真实 0.705/0.680——高分藏在低密度区。采集函数的探索项（κσ）对症。
- **L3.5 无引导的重启是浪费**（09-05 v4）：iter11 后 4 次重启烧 120 等效预算买 0 分。重启注入要么代理引导、要么膨胀 σ+提高随机配额。
- **L3.6 对比要打最强对手**（09-05 sweep 教训）：PSO 超参出圈 test 崩 8 个点；基线必须用 sweep 最优配置（r01）。
- **L3.7 死因驱动的修复清单化**（09-05 v4）：每处改动对应一条诊断，消融才能归因。
- **L3.8 两两中点扫描是便宜的覆盖修复**（09-05，待验证）：45 个 pair 中点粗筛 ≈11 等效预算，系统画 2-专家脊地形；两冠军皆 2-专家主导 ⇒ 必然覆盖赢家邻域。SGMS v1p 验证中。

## L4. 论文与方法论

- **L4.1 引理论先核对实现**：MERGEvolve 定理 2 按"t∼U(0,1)"描述 Model Swarms 初始化，但实际代码是 U(0,2)（一半外插）——code vs paper discrepancy 会改变新颖性边界（我们的"唯一出凸包"主张因此降级为"出仿射包"）。
- **L4.2 移植要声明边界**：GENOME 是按其源码重实现（评测后端 vLLM→HF、基座/池不同），论文如实写 reimplementation + 超参对照表；官方代码交叉路径自身有 bug（可能因此默认 cross_rate=0）。
- **L4.3 数据集判别力分层**：推理类（GSM8k/NLGraph/MMLU-pro/DROP）分得出算法（差距 >10%），知识类（MMLU）全平局只配当对照；dev 条数 <100 的（mmlu_pro 70、stem 30）噪声吃掉判别力。主战场：GSM8k+NLGraph+medical 多任务。
- **L4.4 PSO 冠军 sum=1.000 实证仿射包定理**；同时它带负系数——PSO 自己也在用凸包外的解（外插子代 U(0,2) 的作用）。

## L5. 追加（2026-09-05 晚，脊探测后）

- **L5.1 成分复杂度阶梯**（5 次探针实证）：2 成分（flan+oasst）≤0.655 → 3 成分（+负cot）≈0.670 → 4-6 成分（+code+、science−、gpt4+）=0.705-0.715。最优解在**成分数上有门槛**；只做 pair 提名/2-稀疏生成的算法有结构性上限。
- **L5.2 协同效应实锤**：flan 单独 0.555 vs 混合 0.655-0.670（+10 分以上），flan×oasst 协同为全场最强交互项（与冠军地图一致）。
- **L5.3 SGMS v2 预案**（若 v1 卡 0.68）：a) 协同生成器从"对支持"升级为"对+背景扰动"（在 pair 上加 2-3 个 ±0.1 低幅第 4-6 成分）；b) 新增"成分扩张"生成器：对 g 的低|α|维度加 ±0.1-0.15 扰动（冠军与 3 成分脊点的差异模式）；c) DE 权重不变（差分天然多成分）。
- **L5.4 探针经济学**：5 次评测买断了"2-3 成分能否赢"的问题——低价探针先于高价全流程，值得固化为流程（先探结构再跑算法）。
- **L5.5 nlgraph 赢家在默认 box 外**（09-05 提前解剖）：PSO nlgraph 冠军 = wizard +1.01, sharegpt **−0.98**, cot +0.78——极端外插解；SGMS 默认 box [−0.5,1.5] 数学上排除该区域。对策：box 边界按数据集配置（nlgraph/gsm8k 用 [−1.5,2.0]）。**先看赢家住哪，再定约束边界。**
- **L2.6 运行中 bash 看不到脚本编辑**：bash 启动时预读整个小文件（<8KB）入内存，等待中的链实例不会执行后续编辑——改等待链脚本必须杀旧实例重启新实例；heredoc 创建的脚本注意变量在创建时已展开（PID 硬编码）。
- **L2.7 pgrep -f 自匹配自杀**：命令文本里含目标名字符串时 `kill $(pgrep -f xxx)` 会杀掉自己的 shell（exit 144）。对策：括号技巧 `pgrep -f "xx[n]xxx"` 或直接用已知 PID。
- **L5.6 首胜记录**（09-05 18:40）：LP v4 nlgraph dev 0.365→**0.550**（test 0.537，预算 ~213）击败 PSO 基线 0.48（~280）。冠军 sum=**1.834**——**PSO 定理级不可达**，span 逃逸主张的实战铁证；PSO 冠军(sum=1.000)与 LP 冠军距离 2.403，同池多解、sharegpt 在两解中角色相反(−0.98 vs +0.95)。机制：停滞 17 轮后重启破局（v4 修复在地形崎岖任务上的价值兑现；与 hellaswag 上的"浪费"形成地形依赖对照）。dev-test 差仅 1.3 分（冠军复评有效）。
- **L2.8 fake_eval 的盲区：局部 def 的名字绑定陷阱**（09-05 18:42 事故）：fake 块里直接 `def eval_batch` 会让该名字成为 main 的局部变量，真实路径调用即 NameError——干跑反而测不到（干跑恰好赋值了）。对策：fake 桩一律用 `globals()["name"] = ...` 重绑定 + AST 检查 main 内无这些名字的局部绑定 + 新脚本上线前跑一次真实微型 GPU run（GENOME 因缺这步两连崩）。已修 search_genome/search_sgms；search_lp 本来就是 globals 写法。
- **L2.9 磁盘满 = 链式灭绝**（09-05 22:41 事故）：/data 3.6T 到 100%（仅剩 71MB）时，v1p 写 safetensors ENOSPC 崩溃 → 主链后续 6 个 run 在满盘窗口全部瞬崩 → 终极链日志都写不出、悄然消亡。教训：a) 长队列必须带磁盘水位检查（复兴链已实现每 run 前打印 df）；b) 已完成 run 的 tmp 物化和 particle 权重是最大可再生空间（本次清出 86G）；c) 事故后要"伤亡清点"——逐链核实日志，不能假设队列还活着。
- **L2.10 自匹配陷阱第三形态**：heredoc 正文含 "python search" 字样 → 启动命令的 cmdline 携带该串 → 新链的 pgrep 忙检查误杀自己。规律：**任何 pgrep/kill 模式与同命令的其余文本做字符串碰撞检查**，含 heredoc。
- **L6.1 跨服务器协作铁律**（09-10 事故）：向协作机（214）发文件时直接 scp 覆盖了对方改过的 evaluate.py——对方的工作版有未提交的本地修改（subset_start 等），覆盖即丢失。**规则：a) 任何覆盖他人环境的文件前，必须先 `git diff`/备份对方版本（如 cp 到 .bak.218 或拉回本机）；b) 用户授权范围 = 只发算法文件，运行/进程/队列由对方机器的主人控制——不自作主张起停别人的任务；c) 两边环境差异（conda、依赖、transformers 版本）意味着"在我这跑通"≠"在那跑通"，发版前先在对方环境做 import 冒烟；d) 远程 pkill 的自匹配陷阱：命令行里同时含目标名和 nohup 重启文本时会自杀，kill 逻辑一律落盘成脚本执行。**
- **L7.1 清理误杀在跑的 run**（09-22 00:33 事故）：巡检磁盘清理时 glob 了 sumo2_* 全部 tmp 目录，把正在跑的 mmlu/medical 的物化目录删掉 → 两 run 崩 + abstainqa 连带。规则：**清理只允许删 log.txt 含 final metrics 的 run 的 tmp**（已完成才可删）；或清理前 pgrep 确认无进程引用该目录。

## L8. RACER 冻结战役（2026-10）

- **L8.1 身份哈希把调度工具自己也锁进快照**：给 `tools/run_racer_campaign.py` 加 `--resume`（阶段三正式矩阵必需）后，该文件及其测试文件都是 identity dependencies → 门禁 cohort 全部快照瞬间漂移，后续 worker 全部 0.3s 身份失败。教训：**身份契约覆盖的工具代码一旦改动，在跑 cohort 必须立即评估漂移面，不能边跑边改调度器**；处置按冻结计划"需要改代码则新版本整 cohort 重跑"——旧门禁归档为 `racer_gate_v1_superseded`（留吞吐证据，不拼接成功 run），新身份下重开 25 run 全量门禁。
- **L8.2 Edit 的 old_string 笔误要多试一次读原文**：两次 Edit 失败都源于凭记忆写 old_string（`not only` vs `not only_ids`）而非文件漂移。长函数改前先 grep/sed 定位实际文本再编辑，比重试猜测便宜。
- **L8.3 账本语义靠真实运行核验**：门禁实测确认 racer 预算 4000/4800 提前停不是 bug——整轮 reserve（12 提案×50 粗评+最坏晋升）不足即停，属设计内保守计费；physical==budget_used、test_samples=0、终选=完整 dev 首次观测 raw argmax 均与实现一致。
- **L8.4 串行复用同一卡需要释放尾窗**：worker 退出后 GPU 显存/util 瞬时残留（mem=1~160MiB）会被 fail-closed 判 busy。wait_release_window 只在自己 worker 退出后的窗口做有界稳定等待，不降阈值——门禁 G2 nlgraph 4 连发实测有效。
- **L8.5 oracle 物化无自动回收，磁盘是 4 并发的硬约束**（10-24 01:50 事故预防）：RealOracle 每候选物化 36MB adapter 且从不回读/清理，240 矩阵 4 并发增速 ~14G/h，启动 1.5h 即逼近满盘（6.5G 剩余）。代码事实：运行中 worker 只用当次 cand（评分记录进 item_cache/checkpoint），历史 adapter 唯一作用是 resume 一致性校验（`adapter_names` 全在才可恢复）。处置：保运行舍恢复——按 run 清到只剩最近 3 个物化（PRUNED_LIVE.txt 记账），崩溃则整 run 重跑（概率远低于必然满盘）；Monitor 内嵌磁盘下限自动修剪（<10G 触发）。根因：门禁单卡串行只积 0.7G/run 没暴露并发放大 4×+ 长队列的乘积。**教训：涉及逐候选物化的搜索，磁盘消耗 = 并发数 × 候选数 × 单物化大小，启动前先算乘积并设计回收策略。**
- **L8.6 任务名 ≠ 数据集名，test 路径要用 datasets[0]**（10-28 事故）：`search_frozen.py` 的 evaluate_test 把任务名 `kcross` 当数据集名传给 evaluate.evaluate_test，而该任务的文件是 `knowledge_crosswords.json`——D 组 12 run 全部 FileNotFoundError。9 个主任务恰好 task==dataset 所以从未暴露；multitask 走别的展开路径也不受影响。**教训：任务→数据集的映射层（TASK_REGISTRY）一旦存在别名/多数据集，所有直接调用评分后端的路径都要过映射，不能拿任务名当数据集名；修复合回归测试锁死映射行为，处置按冻结纪律——kill 在跑、TaskStop driver、AskUserQuestion 请示后只重跑受影响组、旧身份保留 + 披露拼接。**
- **L8.7 结果工具自己也会漂移出验证语义**（10-29）：racer_results.py 三处修复（symlink 误拒、job.run 含调度器 status 键、跨实例合并）都是在"验证别人的 run"时发现验证器自身的假设错误。**教训：fail-closed 验证器的每个拒绝条件都要对"真实成功 run"校准——symlink 是 HF 缓存常态而非攻击、调度器给 job.run 加状态键是正常生命周期；验证器不在身份依赖清单内 ≠ 可以不修，但修完要把修复语义写进代码注释与披露文档。**
- **L8.8 四实例合并验证需要字节级分身**（10-29）：AC/BD 快照要求原始 search_frozen.py 字节、D1/D2 要求修复后字节，单一工作区无法同时满足两种身份核验。**教训：多身份 cohort 合并验证时，先从快照 sources 反推各身份要求的精确文件字节（旧块替换回去 + sha256 校验），cp 到位→验证→cp 回来；验证器本身要支持多 campaign 合并以免手工拼接漏洞。**
- **L8.9 冻结矩阵的负结果同样可发表**（10-29 定稿）：240 run 冻结矩阵完成后的诚实结论清单——truthfulqa 上 random 最优、kcross 搜索负增益、medical 的 full_eval（取消竞速）反超且省 30% 时间、nlgraph 的 no_rung2/standard_SH 反超、plateau 切换全程零贡献、固定 scale 网格无稳定收益。**教训：预注册 + 等预算 + 证据链验证的框架下，组件价值的任务画像反转和搜索负增益任务的存在，比"全任务全组件占优"的不可复现主张更有方法学价值；论文按任务画像分述，不写普遍最优。**
